## §1 Normal questions

Next. Normal questions.

Q1. What is automatic reference counting? (30. 45s) Answer points (frame first): Compile-time retains/releases for class instances (not a Java-style GC pause model) Strong count. 0 runs deinit One reliability hook without inventing unproven memory metrics (S8 culture ) Agenda opener: “automatic reference. counting is how Swift manages class instance lifetimes with reference counts…” Full spoken answer: “automatic reference counting is. Automatic Reference Counting. the compiler inserts retain and release calls for class instances. Each strong reference bumps the count. when it hits zero, the object is destroyed and deinit runs. It’s not a tracing garbage collector, so we don’t get GC pause semantics. but we do have to break retain cycles ourselves with weak or unowned. At BookMyShow, reliability meant holding a 99.95%+ crash-free bar at 30L+ DAU. lifecycle and memory bugs sit in that same reliability conversation. not as an afterthought.” Common wrong answer: “Swift has a garbage collector like Java.” / “automatic reference counting. pauses the app to collect.” Follow-up ladder: Level: Ask, Point + short answer. L1: Do structs use automatic reference counting?, Value types aren’t refcounted as objects. nested classes still are.. L2: When does deinit run?, When the last strong reference is released. deterministic relative to that release.. L3: automatic reference counting vs MRC?, Manual retain/release era vs compiler-inserted. same runtime idea, less human error.. Provenance: Verified · S8 reliability culture Q2. weak vs unowned? (45s) Answer points (frame first): weak = optional, zeroing. safe if other side dies first unowned = non-optional, non-zeroing. crash if dangling Prefer weak for escaping async / U I callbacks Agenda opener: “Both avoid incrementing the. retain count, but they differ when the object dies…” Full spoken answer: “weak is an optional reference that. doesn’t keep the object alive, and it becomes nil when the object deinits. so you guard let self. unowned also doesn’t keep it alive, but it isn’t optional and isn’t zeroed. if you touch it after deinit, you crash. I use weak for network, ads, and U I callbacks where lifetime is uncertain. I only use unowned when lifetimes are provably nested. like a child object that cannot outlive its parent by construction.” Common wrong answer: “They’re the same. unowned is just faster so I always use it.” Follow-up ladder: Level: Ask, Point + short answer. L1: Why is weak optional?, Because it must represent “already gone.”. L2: When is unowned justified?, Child owned by parent. child never escapes parent’s lifetime.. L3: What about unowned(unsafe)?, Skips safety checks. not casual app code.. Provenance: Learning-lab · capture-list discipline Q3. What’s a common retain cycle in Swift? (45s) Answer points (frame first): Object stores escaping closure. closure captures self strongly Counts never hit zero. abandoned but reachable Fix with capture list [weak self] Agenda opener: “The classic one is an object that. owns a closure that captures itself…” Full spoken answer: “The textbook cycle is a view controller or service. that stores an escaping completion handler, and that handler strongly captures self. Now self owns the closure and the closure owns self, so retain counts never reach zero. the object is abandoned but still reachable. The fix is a capture list: [weak self] plus a guard. Same shape shows up with delegates stored strongly, timers, and. notification blocks.” Common wrong answer: “Any closure that mentions self is a leak.” (non-escaping often fine) Follow-up ladder:. Level: Ask, Point + short answer. L1: Escaping vs non-escaping?, Escaping can outlive the call. cycle risk.. L2: How do you detect it?, Memory Graph / missing deinit. not Leaks.. L3: Nested closures?, Each escaping edge needs capture discipline.. Provenance: Learning-lab · RetainCycleDemo.swift Q4. Should delegates be weak? (30. 45s) Answer points (frame first): Class-bound delegates: yes, weak var to avoid VC ↔ delegate cycles Need AnyObject. (or class-only) for weak Value-type “delegate” patterns differ Agenda opener: “For class delegates in U I kit-style APIs. yes. make them weak…” Full spoken answer: “If the delegate is a class. typically a view controller. storing it strong creates an easy cycle when the child also owns its parent logically. So we declare weak var delegate and constrain the protocol to AnyObject. That way the child doesn’t keep the parent alive. If you’re using struct-based callbacks, you usually pass closures with explicit capture lists instead of a weak delegate. property.” Common wrong answer: “Delegates are always strong so they don’t go nil.” Follow-up ladder: Level: Ask. Point + short answer. L1: Why AnyObject?, Weak references require reference types.. L2: Closure vs delegate?, Closures need capture lists. same ownership problem.. L3: multicast delegates?, Often separate bag with weak boxes. still avoid strong loops.. Provenance: Learning-lab · U I kit patterns Q5. Memory leak vs abandoned memory? (60s) Answer points (frame first): True leak = unreachable allocated memory Abandoned = still referenced but unused (retain. cycles, immortal caches) Tools: Leaks vs Memory Graph / Allocations. do not swap them Agenda opener: “I separate unreachable leaks from reachable abandoned memory…” Full spoken answer: “A. true leak is memory that’s allocated but has no live references. nothing can touch it, so it can never be freed. Abandoned memory still has references. classic retain cycles or caches that never evict. but the app no longer needs those objects. Retain cycles are abandoned and still reachable, so they typically do not show in the Leaks instrument. I use Memory Graph to see ownership edges and Allocations to see persistent growth. Leaks is for unreachable cases. High watermark is different again. peak usage that may drop later.” Common wrong answer: “Retain cycles show up in Leaks.” Follow-up ladder: Level:. Ask, Point + short answer. L1: Why can’t Leaks see cycles?, Because pointers still exist. objects are reachable.. L2: What’s a high watermark?, Peak bytes. not necessarily a leak.. L3: Jetsam relation?, Abandoned heaps raise pressure. OS may kill the app.. Provenance: How I would apply it · Instruments triage Q6. Does [weak self] always fix cycles? (45. 60s) Answer points (frame first): Only breaks that specific closure. self edge Other owners (timer, NC, nested closures, singleton) may remain Still need invalidate / remove / cancel. Agenda opener: “It fixes the capture edge. not every ownership bug…” Full spoken answer: “[weak self] only weakens that closure’s reference to self. If a Timer is still retaining you via target-selector, or a NotificationCenter block is registered without teardown. or another nested escaping closure captures self strongly, you can still fail to deinit. So weak is necessary for escaping closures, but the checklist is broader: timers invalidate. observer tokens removed, tasks cancelled, delegates weak, caches bounded.” Common wrong answer: “I put weak self everywhere. so I can’t have leaks.” Follow-up ladder: Level: Ask, Point + short answer. L1: Example that weak doesn’t fix?, Timer target-selector without invalidate.. L2: Nested escaping?, Inner closure can re-introduce strong self.. L3: When strong self is ?, Non-escaping work. or intentional ownership with clear teardown.. Provenance: Learning-lab Q7. deinit not called. checklist? (60s) Answer points (frame first): Still has ≥1 strong owner. not “automatic reference counting broken” Walk: closures, timer, observers, delegate. nav/presented, singleton cache Confirm with Memory Graph Agenda opener: “If deinit doesn’t run. something still strongly owns the object…” Full spoken answer: “First I assume the object is still retained. automatic reference counting isn’t randomly broken. I check escaping closures and tasks, repeating timers that weren’t invalidated. NotificationCenter tokens still registered, strong delegates, and whether the controller is still in a navigation stack. presented, or held by a singleton cache. Then I’d open Memory Graph and inspect who points at the instance. Once I break the unexpected strong edge, deinit should fire. I’d verify with Allocations that the type doesn’t persist across navigation generations.” Common wrong answer: “Swift bug /. need to call deinit manually.” Follow-up ladder: Level: Ask, Point + short answer. L1: Can you call deinit?, No. runtime calls it when count hits zero.. L2: Print in deinit ?, Fine for lab. remove before ship or guard with debug flags.. L3: Graph vs Allocations?, Graph = who. Allocations = growth over time.. Provenance: How I would apply it · Memory Graph triage Q8. Value types and automatic reference counting? (30. 45s) Answer points (frame first): Structs/enums aren’t automatic reference counting’d as heap objects the same way Stored class. references inside values still refcount Closures can keep class graphs alive Agenda opener: “Value types themselves aren’t reference-counted. but they can hold references…” Full spoken answer: “Structs and. enums are value types. copying them doesn’t use automatic reference counting the way class instances do. But if a struct stores a class reference, that reference is still strong and retains the class. Closures are reference types under the hood, so a struct that somehow participates in escaping closure graphs can. still keep objects alive. So ‘we only use structs’ doesn’t automatically mean ‘no retain cycles’ if classes and. closures are in the mix.” Common wrong answer: “If I use structs I can’t have memory issues.” Follow-up. ladder: Level: Ask, Point + short answer. L1: copy on write connection?, Collections share buffers until mutation. different topic, still refs under the hood.. L2: Actor / class boxes?, Reference semantics return when you wrap.. L3: Why classes for U I kit VCs?, Identity + inheritance / U I kit object graph.. Provenance: Learning-lab · language model Q9. Autorelease pools. when? (45s) Answer points (frame first): Drain temporary ObjC / bridged objects in tight loops Lowers peak watermark. not a cycle fix Mention only when relevant Agenda opener: “Autorelease pools are about temporary peak memory. not retain cycles…” Full spoken answer: “Autorelease pools let you drain temporary autoreleased objects sooner. useful in tight loops that create lots of bridged ObjC temporaries, like some image or string processing paths. That reduces high watermark. It does not break retain cycles. If the interviewer asks about climbing memory from a cycle, I talk weak captures and Instruments Graph. not autorelease pools.” Common wrong answer: “Wrap everything in autoreleasepool to fix leaks.” Follow-up ladder: Level: Ask. Point + short answer. L1: Default pool?, RunLoop drains pools. tight loops may need explicit ones.. L2: Pure Swift structs loop?, Often unnecessary.. L3: Relate to jetsam?, Lower peak can help pressure. still fix abandonment separately.. Provenance: Learning-lab Q10. How do you prevent leaks with async Task? (60s) Answer points (frame first): Task retains strongly captured locals / self Cancel on disappear / deinit Prefer. [weak self] when task may outlive the screen Agenda opener: “Treat unstructured Tasks like escaping closures with cancellation…”. Full spoken answer: “A Task keeps alive anything it strongly captures for as long as it runs. If a view controller fires a task and the user pops the screen. a strong self capture can keep the controller around until the task finishes. I store the task, cancel it in deinit or onDisappear. and use [weak self] inside when the work is optional after teardown. Structured concurrency children cancel with their parent, which is preferable when the A P I allows it.” Common. wrong answer: “async/await means automatic reference counting doesn’t matter.” Follow-up ladder: Level: Ask. Point + short answer. L1: Task vs Task.detached?, Detached is unstructured and easier to forget. be stricter.. L2: Cancellation cooperative?, Check Task.isCancelled / try Task.checkCancellation().. L3: Combine cancellables?, Same idea. store and cancel on teardown.. Provenance: Learning-lab · concurrency ownership Q11. How does a Timer create a retain cycle / keep a target alive? (45. 60s) Answer points (frame first): Target-selector A P I retains the target until invalidate Repeating timer. object may never deinit Invalidate in deinit (and on leave-screen). prefer block + weak Agenda opener: “The important detail is that scheduledTimer with target:selector retains the target…” Full. spoken answer: “When you use Timer.scheduledTimer(timeInterval:target:selector:…), the timer strongly retains the target until you call invalidate. For a repeating timer on a view controller, that means the controller can live forever even after you. think you dismissed it. The fix is to invalidate in deinit and usually when leaving the screen. and set the timer property to nil. Block-based timers with [weak self] avoid the selector retain semantics for self. but you still invalidate so the RunLoop drops the timer.” Common wrong answer: “Timers don’t retain anything. only closures do.” Follow-up ladder: Level: Ask, Point + short answer. L1: One-shot timer?, Still retains until it fires / invalidate. know the A P I.. L2: RunLoop role?, Timer scheduled on a run loop. invalidation removes it.. L3: Display link?, Similar ownership discipline. invalidate on teardown.. Provenance: Learning-lab · TickerFixed in demo Q12. NotificationCenter block observers. what must you remember? (45. 60s) Answer points (frame first): Block A P I returns a token. store it Remove observer using the token on teardown [weak self] inside the block Agenda opener: “With the. block A P I, ownership is token plus capture list…” Full spoken answer: “addObserver(forName:object:queue:using:) returns an observer token. I store that token on the object and remove it in deinit or when stopping observation. Inside the block I capture [weak self] so the center’s ownership of the block doesn’t keep my controller. alive forever. Forgetting either the token removal or the weak capture is a common abandoned-memory bug. I don’t rely on ‘Leaks will tell me’. I’d expect Memory Graph to show the observer graph.” Common wrong answer: “NotificationCenter never retains. you never need tokens.” Follow-up ladder: Level: Ask, Point + short answer. L1: Selector-based A P I?, Different retain rules historically. still remove in deinit on older patterns.. L2: Queue parameter?, Delivers on that queue. main for U I.. L3: Combine publishers?, NotificationCenter.default.publisher. store AnyCancellable.. Provenance: Learning-lab · TimeZoneObserver.

T1. unowned self in an async callback after the VC is dismissed (90s) Answer points (frame first): Trap: unowned. for “cleaner” syntax Callback can outlive VC. dangling. crash Prefer weak + guard. tie to network/ad S D K realities Agenda opener: “I’d treat that as a lifetime bug waiting to. happen…” Full spoken answer: “If a view controller dismisses while a network or ad callback is still outstanding. unowned self becomes a dangling reference the moment deinit runs. The next callback touch crashes. That’s why I default to [weak self] for escaping async work. unowned is for nested ownership you can prove in one sentence. not for URLSession or third-party S D K completions. In a reliability culture like BMS. Verified S8 with Crashlytics and a high CFS bar. this class of crash is exactly what triage workflows exist to catch. How I would apply Instruments here: reproduce dismiss-during-flight, confirm with Graph that the VC is gone. and ensure the callback path is weak-safe.” Common wrong answer / trap: “unowned is fine if I’m careful. about timing.” Follow-up ladder: Level: Ask, Point + short answer. L1: Why crash not nil?, unowned doesn’t zero.. L2: weak + continue work?, Often cancel work on disappear instead of updating U I.. L3: MainActor implication?, Still need lifetime safety. actor isolation ≠ ownership.. Provenance: Verified · S8 crash culture + How I would apply it · weak callbacks T2. NotificationCenter + closure observer cycle (90s) Answer points (frame first): Center holds block. block holds self. self holds token/lifetime Store token. remove. weak capture Don’t say “Leaks will catch it” Agenda opener: “The bug is usually forgotten token removal or. a strong self capture…” Full spoken answer: “With the block A P I. NotificationCenter keeps the block. If that block strongly captures self, and self stays alive because of other reasons. or you effectively keep the observation for the app lifetime. you can abandon controllers or create hard-to-see ownership. The correct pattern is: store the returned token, remove it on teardown. and capture [weak self] in the block. If deinit isn’t firing, Memory Graph is the right tool. Depending on what’s stored, that can create a cycle or at least confusing lifetime. The senior move is to avoid referencing self inside lazy initializers when possible. pass needed values explicitly. or don’t store an escaping self-capturing closure as a property. Marking one closure [weak self] while others stay strong doesn’t save you. I either weaken all escaping handlers, or better redesign: use a delegate. a single pipeline, or structured concurrency with cancellation so the collection doesn’t immortalize the owner.
